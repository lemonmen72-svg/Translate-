# Предлагаемая архитектура

Опирается на `00-brief.md` (ТЗ) с поправками из `01-research.md`. Код ещё не
написан — это план структуры, чтобы решения из разбора были зафиксированы до
первой строки.

## Модульная структура

```
:app          Compose UI: выбор языка, «скорость vs качество», история, запуск сессии
:core         Оркестрация пайплайна, машина состояний, back-pressure, модель истории
:capture      MediaProjection + AudioRecord → 16 кГц моно PCM
:vad          Silero VAD, нарезка на фразы (sherpa-onnx)
:asr          интерфейс AsrEngine; реализации: sherpa-onnx, whisper.cpp
:mt           интерфейс Translator; реализации: opus-mt(ONNX), nllb(ONNX), NoOp(ru→ru)
:tts          опционально; интерфейс TtsEngine; Piper / Silero
:overlay      SYSTEM_ALERT_WINDOW окно субтитров
:bench        офлайн-прогон записанных WAV через пайплайн + замер задержки по стадиям
```

Разбиение по модулям не ради красоты: `:asr` и `:mt` обязаны быть за
интерфейсами, потому что по §3 и §4 разбора выбор конкретных моделей ещё не
зафиксирован и с высокой вероятностью поменяется после первых замеров.

## Поток данных

```
MediaProjection ──► AudioRecord (16 кГц моно PCM)
                        │
                        ▼
                  кольцевой буфер
                        │
                        ▼
                  [опц.] денойз (GTCRN)          ← флаг, по умолчанию выкл.
                        │
                        ▼
                  Silero VAD ──► сегмент завершённой фразы
                        │
                        ▼
              ограниченная очередь (drop-oldest)  ← §11 разбора
                        │
                        ▼
                  ASR (forced language, без conditioning на историю)
                        │
                        ├──► фильтр галлюцинаций (no_speech_prob / avg_logprob / compression_ratio)
                        │        отбросил → индикатор «пропущено», дальше не идём
                        ▼
                  [опц.] восстановление пунктуации
                        │
                        ▼
                  MT (+ контекст 1–2 предыдущих фраз)   ← при source=ru: NoOp
                        │
                        ├──► оверлей с субтитрами
                        └──► [опц.] TTS ──► приостановка подачи в VAD на время проигрывания (§7)
```

Две развилки, вытекающие прямо из разбора:

- **source = ru** — MT-стадия заменяется на `NoOpTranslator`, модель перевода
  вообще не загружается. Экономит RAM и убирает 0.3–2 с из бюджета.
- **TTS включён** — на время проигрывания подача в VAD приостанавливается,
  иначе пайплайн распознаёт собственный голос.

## Оркестрация

Kotlin coroutines. Между стадиями — `Channel` с `BufferOverflow.DROP_OLDEST` и
малой ёмкостью (1–2 элемента). Это и есть реализация решения из §11: при
отставании ASR теряем фразу, но не накапливаем отставание.

Каждая стадия помечает сегмент временными метками входа/выхода. Метки идут
в лог и в `:bench` — без этого настраивать бюджет задержки из §3 придётся на
ощупь.

## Машина состояний (для индикатора из UX-раздела ТЗ)

```
Idle → RequestingConsent → Listening ⇄ Recognizing → Translating → Speaking? → Listening
                                 ↓
                              Skipped (галлюцинация / drop по back-pressure)
                                 ↓
                              Throttled (по тепловому статусу)
                                 ↓
                              Stopped / Error
```

`Skipped` и `Throttled` — не декорация. ТЗ просит индикатор, «чтобы было
понятно, что происходит, а не зависло ли»; именно эти два состояния иначе
выглядят как зависание.

## Конфигурация «скорость vs качество»

По §3 разбора это не удобство, а переключение между двумя режимами, один из
которых укладывается в заявленную задержку, а другой нет.

| Профиль | ASR | MT | VAD min_silence | Ожидаемая задержка |
|---|---|---|---|---|
| Speed | whisper-tiny/base int8 | Opus-MT (~75M) | 300 мс | 1.5–3 с (цель ТЗ) |
| Quality | whisper-small int8 + KV-cache | NLLB-600M int8 | 600–700 мс | 4–6 с |

Профиль Quality честно называть в UI медленным, а не «лучшим» — иначе
пользователь выберет его и решит, что приложение сломано.

## Требования к железу

Нижняя граница по аналогии с RTranslator — **6 ГБ RAM** для профиля Quality.
Профиль Speed должен работать и на меньшем; это стоит проверить замером, а не
предполагать.

## Порядок вызовов MediaProjection (Android 14/15)

Порядок строгий, нарушение даёт `SecurityException` (§2 разбора):

1. `MediaProjectionManager.createScreenCaptureIntent()` → системный диалог;
2. запуск foreground service с типом `mediaProjection`;
3. `getMediaProjection(resultCode, data)` — **Intent не кэшировать**, каждая
   сессия получает свой;
4. `AudioPlaybackCaptureConfiguration.Builder(projection)` + usage
   `USAGE_MEDIA` / `USAGE_GAME` / `USAGE_UNKNOWN`;
5. `AudioRecord.Builder().setAudioPlaybackCaptureConfig(...)`.

Манифест: `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_MEDIA_PROJECTION`,
`RECORD_AUDIO`, `SYSTEM_ALERT_WINDOW`, `POST_NOTIFICATIONS`.

## Модели: где лежат

Модели в APK не кладём — суммарно это сотни мегабайт, а под каждый язык нужен
свой набор. Скачивание при первом выборе языка, в приватный каталог приложения,
с проверкой контрольной суммы. Один язык — один набор; не загружать модели для
языков, которые пользователь не выбрал.
